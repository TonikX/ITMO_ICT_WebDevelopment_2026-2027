# APEX · Лабораторная работа № 2

**Данилевский Тимур Давидович · K3339 · Вариант 6 — табло победителей автогонок.**

Python 3.10 / Django 3.2.25 / Jinja2 / PostgreSQL 16. Интерфейс на собственном CSS, анимация GSAP.
Изображения, шрифты и JavaScript хранятся локально. Сайт не требует npm-сборки и внешних CDN.

## Быстрый запуск на macOS

Включите Docker Desktop, затем в этой папке запустите:

```bash
bash run.command
```

Скрипт создаст локальное виртуальное окружение, установит зависимости, запустит отдельную
PostgreSQL-базу, применит миграции, добавит учебные данные и запустит Django.
База привязана к `127.0.0.1:54329`; другие проекты и базы не изменяются.

Откройте **http://127.0.0.1:8000/**. Для остановки Django нажмите `Ctrl+C`.

## Ручной запуск на macOS / Linux

Нужны Python **3.10** и Docker с Compose v2. Перейдите в папку этого README.

```bash
python3.10 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
cp .env.example .env
docker compose -p itmo-apex-lab2 up -d --wait
python manage.py migrate
python manage.py seed_demo
python manage.py runserver
```

Если команда `python3` указывает на Python 3.10, её можно использовать вместо `python3.10`.

На Windows создание окружения и активация:

```powershell
py -3.10 -m venv .venv
.venv\Scripts\Activate.ps1
Copy-Item .env.example .env
```

Остальные команды те же. Если нет Docker, можно подключить существующий PostgreSQL,
изменив значения `POSTGRES_*` в `.env`. Пользователь PostgreSQL должен владеть базой;
для тестов ему требуется право `CREATEDB`.

|---|---|---|

рассчитываются относительно даты первого заполнения.

Все соревнования, участники и результаты вымышлены. Фотографии — иллюстрации автоспорта,
не фотографии учебных событий. Источники и лицензии: `static/credits.txt`.

## Что реализовано

- Регистрация, вход, выход POST-запросом.
- Календарь гонок с поиском, фильтром статуса и пагинацией.
- Гонка с таблицей **всех заездов**, поиском и фильтром класса; стартовый список.
- Профили гонщиков: ФИО, команда, автомобиль, описание, опыт, класс.
- Создание, изменение и удаление своих заявок; уникальный номер и лимит мест.
- Комментарии с периодом заезда, типом, оценкой 1–10 и автором из сессии.
- Судейский интерфейс Race control: создание и изменение времени и результата.
- Django-admin для всех моделей.
- Проверка ролей и владения на сервере, CSRF, экранирование пользовательского текста.
- Адаптивный дизайн, клавиатурный фокус, режим reduced motion.

Редактирование и отмена заявки разрешены, пока регистрация открыта и у заявки нет результатов.
Профиль гонщика общий для всех его заявок. DNF / DSQ не получают место, финиш требует время и место.

## Проверки

```bash
python manage.py check
python manage.py makemigrations --check --dry-run
python manage.py test tests --verbosity 2
```

32 интеграционных теста проверяют права, формы, уникальность, ограничения, пагинацию,
комментарии, судейские результаты и Django-admin. Основной прогон выполнен на PostgreSQL 16.

Для облегчённой проверки без PostgreSQL можно **явно** включить SQLite:

```bash
USE_SQLITE=1 python manage.py migrate
USE_SQLITE=1 python manage.py seed_demo
USE_SQLITE=1 python manage.py runserver
```

Этот режим не заменяет PostgreSQL при сдаче: блокировки `select_for_update` в SQLite не работают.

## Отчёт

Из корня репозитория:

```bash
pip install -r requirements-docs.txt
mkdocs serve --dev-addr 127.0.0.1:8001
mkdocs build --strict
mkdocs gh-deploy
```

Исходники отчёта: `docs/lr2/`. Конфигурация: `mkdocs.yml`. Для GitHub Pages выберите ветку
`gh-pages`, каталог `/ (root)` в Settings → Pages. Django-приложение на GitHub Pages не запускается;
там публикуется только отчёт.

## Остановка PostgreSQL

```bash
docker compose -p itmo-apex-lab2 stop
```

Данные сохраняются в отдельном Docker volume. Обычная остановка не удаляет базу.

## Ограничения учебной версии

Django 3.2 выбран строго по заданию; он больше не получает исправления безопасности.
Среда рассчитана на локальную защиту на Python 3.10. Перед публичным развёртыванием требуются
обновление Django, отдельные учётные данные и настройка production-сервера. По умолчанию сайт и БД
слушают только локальный интерфейс.

Уникальность места между разными заявками проверяется моделью; клиентский судейский интерфейс
сериализует запись блокировкой гонки. Одновременные административные изменения через Django-admin
не защищены отдельным межтабличным ограничением уникальности места.

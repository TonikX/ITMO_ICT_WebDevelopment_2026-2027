# Модель и архитектура

## MVT и MVC

Django использует MVT — вариант MVC. Модель отвечает за структуру данных, view обрабатывает запрос, template строит HTML; URLconf направляет запрос в нужный обработчик. Например: URL `/tours/1/book/` → функция `book` → `BookingForm` → ORM `Booking` → перенаправление в личный кабинет.

## Сущности

| Модель | Поля и назначение | Связи |
|---|---|---|
| User | AbstractUser; дата рождения, паспорт, адрес, национальность | 1:M с бронями, отзывами, владениями и удостоверениями |
| Country | Уникальное название страны | 1:M с Tour |
| Agency | Название и контактный email | 1:M с Tour |
| Tour | Название, описание, даты, оплата, цена, доступность | FK страны и агентства |
| Booking | Туристы, пожелания, статус, сохранённая цена, время создания | FK пользователя и тура |
| Review | Даты тура, текст, оценка 1–10, время | FK пользователя и тура |
| Car | Госномер, марка, модель, цвет | M:M с User через Ownership |
| Ownership | Начало/окончание владения | FK пользователя и автомобиля |
| DrivingLicense | Номер, категория, дата выдачи | FK пользователя |

Автовладелец из схемы практики объединён с User согласно практике 2.3. Миграция создаёт конечную схему сразу: `AUTH_USER_MODEL` задаётся до первого `migrate`. Фамилия и имя — унаследованные поля AbstractUser.

## Целостность

Даты тура и владения, рейтинг и число туристов проверяются формами; критичные диапазоны дополнительно защищены CheckConstraint в БД. UniqueConstraint ограничивает повторные бронирования и отзывы. Даты отзыва задаются сервером, не берутся из POST. Историческая цена хранится в бронировании, чтобы изменение цены тура не меняло сумму ранее поданной заявки.

PROTECT на ссылках на справочники и на тур из брони предотвращает случайное разрушение связанных данных. Пересечения интервалов владения проверяются `Ownership.clean()` при вводе через admin; прямой ORM `save()` не вызывает `full_clean()` автоматически. Это учебная проверка, а не защита от конкурентной вставки владений.

`select_for_update()` и транзакции используются при подтверждении и изменении броней. Серверный фильтр пользователя исключает доступ к чужим броням даже при ручной подмене URL. Изменяющие действия требуют POST и CSRF; выход также только через POST. Jinja2 экранирует пользовательский текст.

## Шаблоны

Клиентская часть действительно использует backend `django.template.backends.jinja2.Jinja2`, а не синтаксически похожий Django Template Language. Глобальные функции `url`, `static`, `messages`, `page_url` подключены в `django_project_student/jinja2.py`. Встроенная админка использует второй backend DjangoTemplates. Формы выводятся через BoundField; CSRF — скрытое поле `csrfmiddlewaretoken`.

## Структура

- `django_project_student/`: настройки, корневые URL, Jinja2, WSGI.
- `accounts/`: расширенный пользователь, регистрация, вход и выход.
- `tours/`: предметные модели, формы, FBV/CBV, подтверждение, admin, тесты, demo-команда.
- `project_first_app/`: учебные автомобили и владения.
- `templates/`, `static/`: интерфейсы и CSS.
- `docs/`, `mkdocs.yml`: этот отчёт.
- `requirements.txt`, `.env.example`, `README.md`: зависимости и ручная настройка запуска в PyCharm.

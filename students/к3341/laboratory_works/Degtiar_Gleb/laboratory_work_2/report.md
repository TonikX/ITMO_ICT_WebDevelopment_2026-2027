# Отчёт по ЛР2. Простой сайт на Django

**Вариант 4 — Список туров туристической фирмы.**

## Цель работы

Овладеть практическими навыками разработки веб-приложений средствами Django: проектирования модели данных, работы с ORM и PostgreSQL, обработки запросов, создания форм и шаблонов, регистрации пользователей и разграничения прав доступа.

## Постановка задачи

Разработать сайт туристической фирмы, содержащий сведения о названии тура, турагентстве, описании, периоде проведения и условиях оплаты. Предусмотреть регистрацию пользователей, просмотр и резервирование туров, изменение и удаление собственных бронирований, публикацию отзывов с оценкой от 1 до 10.

Администратор должен подтверждать бронирования средствами Django Admin. В клиентской части необходимо сформировать таблицу проданных туров по странам и реализовать дополнительные действия администратора. Для списков объектов требуются поиск, фильтрация и пагинация; интерфейс должен иметь CSS-оформление.

## Ход выполнения работы

### 1. Подготовка проекта и архитектуры

Создан Django-проект с разделением функциональности на приложения `accounts`, `tours` и `project_first_app`. Подключены PostgreSQL, механизм сессий, аутентификация, сообщения пользователю и CSRF-защита. Для приложений настроены отдельные файлы маршрутизации, подключаемые к главному URLconf через `include()`.

В основу положена архитектура MVT — используемый Django вариант MVC. Модели описывают данные, представления обрабатывают запросы и выполняют прикладную логику, шаблоны формируют HTML. Например, запрос на бронирование направляется в функцию `book`, проверяется формой `BookingForm`, сохраняется через ORM и завершается перенаправлением в список бронирований.

Клиентские страницы используют backend Jinja2. Функции построения URL, подключения статических файлов, получения сообщений и формирования ссылок пагинации зарегистрированы в `django_project_student/jinja2.py`. Для встроенной административной панели отдельно сохранён стандартный backend DjangoTemplates.

### 2. Проектирование базы данных

Выделены справочники стран и турагентств, сущности тура, бронирования и отзыва. Справочники вынесены в отдельные таблицы, чтобы названия стран и агентств не дублировались в каждой записи тура и могли использоваться при фильтрации.

| Модель | Основные данные | Связи |
|---|---|---|
| `User` | Учётная запись, имя, фамилия, дата рождения, паспорт, адрес, национальность | Один пользователь — несколько бронирований и отзывов |
| `Country` | Уникальное название страны | Одна страна — несколько туров |
| `Agency` | Название агентства, email | Одно агентство — несколько туров |
| `Tour` | Название, описание, даты, условия оплаты, цена, признак доступности | Внешние ключи страны и агентства |
| `Booking` | Число туристов, пожелания, статус, сохранённая цена, время создания | Внешние ключи пользователя и тура |
| `Review` | Даты тура, текст, рейтинг, время публикации | Внешние ключи пользователя и тура |

Для денежных значений использован `DecimalField`. Цена копируется из тура в бронирование при создании заявки: последующее изменение цены в каталоге не меняет стоимость уже оформленной брони. Итоговая сумма определяется произведением сохранённой цены и числа туристов.

**Фрагмент модели бронирования — `tours/models.py`:**

```python
    @property
    def total(self): return self.unit_price * self.travelers
```

В базе установлены ограничения на порядок дат, неотрицательную цену, допустимые статусы, рейтинг 1–10 и число туристов 1–20. Уникальность пары «пользователь — тур» исключает повторную бронь и повторный отзыв одного автора на тот же тур. Ссылки на страну, агентство и тур из бронирования защищены от удаления через `PROTECT`.

После описания моделей созданы и применены начальные миграции. Все предметные модели зарегистрированы в Django Admin.

### 3. Регистрация и расширение пользователя

Для хранения дополнительных атрибутов создана модель `User`, унаследованная от `AbstractUser`. Она подключена через `AUTH_USER_MODEL` до применения первой миграции. Связи других моделей обращаются к пользователю через `settings.AUTH_USER_MODEL`.

**Модель пользователя — `accounts/models.py`:**

```python
from django.contrib.auth.models import AbstractUser
from django.db import models

class User(AbstractUser):
    birth_date = models.DateField('Дата рождения', null=True, blank=True)
    passport_number = models.CharField('Номер паспорта', max_length=20, blank=True)
    address = models.CharField('Домашний адрес', max_length=255, blank=True)
    nationality = models.CharField('Национальность', max_length=80, blank=True)
    def __str__(self):
        return self.get_full_name() or self.username
```

Регистрация реализована с помощью формы на основе `UserCreationForm`. Пароль сохраняется штатным механизмом хеширования Django. После успешной регистрации выполняется вход в систему. Дополнительные поля включены в интерфейс создания пользователя и административную панель.

Форма регистрации не содержит полей `is_staff` и `is_superuser`: передача таких параметров вручную не повышает права нового пользователя.

### 4. Каталог и карточка тура

Каталог реализован представлением `TourList` на основе `ListView`, карточка тура — `TourDetail` на основе `DetailView`. Обычным посетителям доступны активные туры; администратор также видит скрытые записи.

В каталоге отображаются страна, агентство, название, описание, период и цена. В карточке приведены подробное описание, условия оплаты и отзывы. Для тура, дата начала которого уже прошла, создание бронирования закрыто.

Обращения к связанным справочникам оптимизированы с помощью `select_related('country', 'agency')`. Создание и редактирование тура доступны администратору непосредственно на сайте через `CreateView` и `UpdateView`.

### 5. Резервирование туров

Создание бронирования доступно авторизованному пользователю. В форме вводятся количество туристов и пожелания. Пользователь, тур и цена устанавливаются сервером и не принимаются из пользовательских полей.

Новая заявка получает статус `pending`. В личном кабинете пользователь видит свои брони, может изменить число туристов и пожелания либо удалить запись после подтверждения действия. Изменение ранее подтверждённой брони возвращает её в состояние ожидания.

Доступ к отдельной брони ограничен на уровне запроса к базе данных:

```python
booking = get_object_or_404(Booking, pk=pk, user=request.user)
```

Поэтому подстановка идентификатора чужой записи в URL не открывает доступ к её изменению или удалению. Операции сохранения завершаются перенаправлением, что исключает повторную отправку формы при обновлении страницы результата.

### 6. Подтверждение бронирований и права доступа

Разделение полномочий реализовано одновременно в шаблонах и представлениях. В шаблонах проверяются `is_staff` и `is_superuser`: административные ссылки доступны только сотруднику или суперпользователю. На сервере используются `login_required`, `StaffMixin` и проверки роли; скрытие кнопок не является единственным ограничением доступа.

| Действие | Гость | Пользователь | Администратор |
|---|---|---|---|
| Просмотр активных туров и отзывов | Да | Да | Да |
| Создание бронирования и отзыва | Нет | Да | Да |
| Изменение и удаление своей брони | Нет | Да | Да |
| Просмотр всех заявок и подтверждение | Нет | Нет | Да |
| Создание и изменение тура | Нет | Нет | Да |
| Просмотр продаж по странам | Нет | Нет | Да |

Подтверждение доступно в разделе заявок сайта и массовым действием Django Admin. Обе операции используют функцию `confirm_booking` из `tours/services.py`:

```python
from django.db import transaction
from .models import Booking

def confirm_booking(pk):
    """Идемпотентное подтверждение; используется сайтом и Django Admin."""
    with transaction.atomic():
        booking = Booking.objects.select_for_update().get(pk=pk)
        booking.status = Booking.CONFIRMED
        booking.save(update_fields=['status'])
    return booking
```

Блокировка строки и транзакция используются при подтверждении и пользовательском редактировании заявки. Повторное подтверждение сохраняет тот же статус. Изменяющие действия на сайте выполняются через POST с проверкой CSRF-токена.

### 7. Отзывы о турах

Реализована форма публикации отзыва с текстом и оценкой от 1 до 10. Автор определяется по текущей сессии. Даты начала и окончания копируются из тура в запись отзыва, поэтому сохраняются независимо от последующих изменений карточки.

В списке отзывов выводятся автор, даты поездки, текст и рейтинг. Повторный отзыв того же пользователя о том же туре отклоняется. Пользовательский текст экранируется при отображении. Возможность написать отзыв предоставлена зарегистрированным пользователям; наличие подтверждённой покупки дополнительно не требуется.

### 8. Таблица проданных туров по странам

На странице `/manage/sales/` сформирован отчёт по подтверждённым бронированиям. В рамках модели проданным считается тур, для которого имеется заявка в состоянии `confirmed`; приём платежей в задание не входит.

Данные группируются по стране и конкретному туру. Для каждой строки рассчитываются количество бронирований, число туристов и сумма продаж. Дополнительно формируется сводка по странам. Используются ORM-агрегации `Count`, `Sum` и выражение произведения цены на количество туристов.

Фильтры применяются до группировки. Сводные значения учитывают все отфильтрованные записи, а не только текущую страницу. Ожидающие заявки в расчёт не входят. При удалении брони или возврате её в ожидание соответствующая сумма исключается из текущего отчёта.

### 9. Поиск, фильтрация и пагинация

Для каталога реализованы поиск по названию и описанию, фильтры страны, агентства, диапазона дат начала и максимальной цены. Доступна сортировка по дате, цене и названию.

Бронирования и административные заявки фильтруются по названию тура и статусу; продажи — по названию и стране. Параметры обрабатываются формами Django: некорректные значения отображаются как ошибки ввода.

На странице размещается шесть записей. Для FBV используется `Paginator`, для списковых CBV — `paginate_by`. При построении ссылок между страницами сохраняются параметры поиска и фильтров.

### 10. Оформление интерфейса

Создан общий базовый шаблон с навигацией, сообщениями и подвалом. От него наследуются каталог, карточка тура, формы, списки бронирований, отчёт продаж и учебные страницы.

Оформление выполнено собственными CSS-стилями: карточки туров, цветовые обозначения статусов, единые элементы форм, таблицы и страницы подтверждения удаления. Для узких экранов предусмотрены изменение сетки и горизонтальная прокрутка таблиц. Декоративная графика реализована средствами CSS, внешние ресурсы оформления не требуются.

### 11. Практические работы 2.1–2.3

Практики включены отдельным приложением `project_first_app`, которое использует общую расширенную модель пользователя.

| Практика | Реализованные элементы |
|---|---|
| 2.1 | Модели автомобиля, владения и удостоверения; миграции; регистрация в admin; FBV карточки владельца; маршрутизация |

Модель `Ownership` содержит даты начала и окончания владения. Валидация модели проверяет порядок дат и пересечения периодов для одного автомобиля при вводе через административную форму. Связь объявлена через явную промежуточную модель:

```python
owners = models.ManyToManyField(
    settings.AUTH_USER_MODEL,
    through='Ownership',
    related_name='cars',
)
```

Первые два владельца последовательно связаны с тремя автомобилями: периоды 2020–2021 и 2022–2023 не пересекаются. В автоматической проверке дополнительно выполняется создание трёх владельцев и трёх автомобилей через формы. Наполнение командой и тестами не заменяет демонстрацию ручного ввода через интерфейс.

## Запуск проекта (кратко)

Требуются Python **3.10**, установленный локальный PostgreSQL и доступ к базе. Команды выполняются из `laboratory_work_2` с выбранным интерпретатором Python 3.10.

```bash
python -m pip install -r requirements.txt
```

При первом запуске в PostgreSQL создаются пользователь и база; SQL-команды выполняются отдельно от имени администратора:

```sql
CREATE USER tour_user WITH PASSWORD 'tour_local_password' CREATEDB;
CREATE DATABASE tour_agency OWNER tour_user;
```

Файл `.env.example` копируется в `.env`; значения `POSTGRES_DB`, `POSTGRES_USER`, `POSTGRES_PASSWORD`, `POSTGRES_HOST` и `POSTGRES_PORT` должны соответствовать локальной базе. Затем выполняются:

```bash
python manage.py migrate
python manage.py seed_demo
python manage.py createsuperuser
python manage.py runserver
```

Сайт доступен по адресу http://127.0.0.1:8000/, административная панель — http://127.0.0.1:8000/admin/. Демонстрационные пользователи `demo1`–`demo6` имеют пароль `Travel-demo-2026!`; учётная запись администратора создаётся командой `createsuperuser`.

В PyCharm используется конфигурация Python: файл `manage.py`, параметры `runserver`, рабочий каталог `laboratory_work_2`. Для просмотра отчёта: `python -m mkdocs serve -a 127.0.0.1:8001`.

В результате работы разработан сайт туристической фирмы «Меридиан», реализующий каталог туров, регистрацию, бронирования, отзывы и учёт подтверждённых продаж по странам. Разграничение прав выполнено в пользовательском интерфейсе и на сервере. Для работы со списками добавлены фильтры, поиск и пагинация.

В ходе реализации применены связи Django ORM, миграции PostgreSQL, функциональные и классовые представления, ModelForm, шаблоны Jinja2 и встроенная система аутентификации. Практики с автомобилями демонстрируют промежуточную M:M-модель и расширение пользователя. Автоматические проверки подтвердили работоспособность основных сценариев и ограничений доступа.

# Проверки и подготовка к защите

## Автоматические проверки

Проверка выполнена на Python 3.10, Django 3.2.25 и **PostgreSQL 16**.
Для тестов Django создаёт отдельную базу `test_apex`, после завершения удаляет её.
Демонстрационная база `apex` при этом не очищается.

```text
python manage.py check
System check identified no issues (0 silenced).

python manage.py makemigrations --check --dry-run
No changes detected

python manage.py test tests --verbosity 1
Ran 32 tests
OK
```

| Область | Проверенные сценарии |
|---|---|
| Страницы и Jinja2 | Публичные страницы возвращают 200, шаблонные конструкции не попадают в HTML |
| Аккаунты | Регистрация и сессия, отклонение слабого пароля, вход, выход только POST, безопасный `next` |
| Доступ | Гость перенаправляется на вход; обычный пользователь получает 403 для судейских URL |
| Владение | Чужую заявку нельзя изменить и удалить; в кабинете пользователь работает со своими данными |
| Заявки | Создание профиля и заявки, изменение, сохранение обновлённого ФИО, подтверждение удаления |
| Ограничения заявки | Повторная регистрация, занятый номер, границы номера, заполненная гонка, закрытая регистрация |
| Результаты и заявки | Изменение и отмена заявки с результатами запрещены |
| Комментарии | Все поля сохраняются; автор берётся из сессии; неверные даты, тип и рейтинг отклоняются |
| CSRF и XSS | POST без CSRF даёт 403; HTML комментария экранируется |
| Судья | Видимость кнопок, создание и редактирование времени, DNF без времени и места |
| Часовой пояс | Дата и время заезда отображаются в Europe/Moscow, а не в UTC |
| Валидация заезда | Неположительное время, неверная дата, повторная попытка, занятое место, участник другой гонки |
| Фильтрация | Поиск, класс, статус, сохранение параметров и некорректные номера страниц |
| База данных | Уникальные номера и диапазон рейтинга проверяются также ограничениями PostgreSQL |
| Django-admin | Судья с правами создаёт заезд через административную форму |

Тесты находятся в `tests/test_racing.py`. Они проверяют бизнес-сценарии через Django Test Client
и реальные ограничения тестовой PostgreSQL-базы. Дополнительно на работающем сервере
через HTTP проверены вход с CSRF-токеном, открытие личного кабинета и выход POST-запросом.

## Проверка интерфейса

Скриншоты сделаны в headless Chrome инструментом `shoot.mjs` из Taste Skill. Публичные страницы
снимались с работающего Django-сервера. Для закрытых страниц получен HTML тем же Django-приложением
после входа через Test Client; затем он отрисован с реальными CSS, шрифтами и изображениями.
Это проверка отрисовки закрытых интерфейсов, а не запись ручного кликового сценария.

Главная просмотрена при ширине 1440, 1024, 820, 768 и 390 пикселей.
Проверялись календарь, гонщики, регистрация, вход,
личные заявки, форма заявки, протокол гонки, Race control, форма результата и Django-admin.

Автоматическая проверка Taste Skill используется как вспомогательный аудит.
Статус его общего gate: **`GATE: OFF (no build active)`**. Полное прохождение правил
лендинга не заявляется: приложение использует собственную серверную структуру.

Первый аудит подтвердил отсутствие горизонтального выхода страницы за экран, наложений
текста и элементов, обрезанного текста, пустых изображений и неназванных контролов. После
аудита исправлены контраст второстепенного текста, подложка вертикальной подписи,
области нажатия ссылок, меню на планшете и поведение прокрутки при клавиатурном фокусе.

Часть замечаний аудитора относится к его обязательному шаблону лендинга: высота каждой секции
ровно один экран, наличие иллюстраций в каждой секции, одна величина всех `h2`, только
определённые пропорции колонок и декоративный scroll-moment. Эти правила не являются
требованиями лабораторной и не применялись к таблицам, формам и компактным информационным блокам.
Фотографии намеренно повторяются в карточках учебных гонок из ограниченного набора иллюстраций.

## Загрузка страницы

После перевода шрифтов в WOFF2 и добавления `srcset` выполнен `perf.mjs` из Taste Skill:

| Показатель | 1440 px | 390 px |
|---|---|---|
| Передано ресурсов | 494.2 КиБ | 378.3 КиБ |
| Изображения | 192.1 КиБ | 76.6 КиБ |
| Шрифты | 159.3 КиБ | 159.3 КиБ |
| Изображения чрезмерного размера | 0 | 0 |
| Ошибки загрузки | 0 | 0 |
| Layout shift | 0.014 | 0.000 |

Итог: **0 FAIL, 4 WARN**. Предупреждения относятся к шести файлам шрифтов и фоновой нагрузке
компьютера; временные показатели локального сервера не трактуются как показатели публичного
хостинга. До оптимизации объём загрузки составлял около 1281 КиБ.

## Ограничения проверки

- Интеграционные тесты запускаются через Django Test Client; отдельного набора Playwright-тестов нет.
- Не проводилось нагрузочное тестирование и тестирование в Safari / Firefox.
- Судейский интерфейс использует транзакционную блокировку гонки; массовая параллельная запись
  результатов из разных сессий Django-admin отдельно не проверялась.
- SQLite разрешён только как явно включаемый упрощённый режим, а не как замена PostgreSQL для сдачи.
- Django 3.2 сохранён для соответствия заданию, а не для публичной production-эксплуатации.

## Вопросы для защиты

**Чем MVT отличается от MVC?** В Django модель отвечает за данные, view обрабатывает запрос,
template формирует HTML. Роль контроллера распределена между view, URL dispatcher и механизмами фреймворка.

**Зачем отдельные Entry и Heat?** Entry — регистрация участника на гонку. Heat — отдельный
заезд. Одна заявка может иметь несколько заездов, поэтому таблица не теряет попытки.

**Почему недостаточно скрыть кнопку судьи?** Пользователь может отправить запрос вручную.
Права проверяются декоратором `staff_only` на сервере, отсутствие кнопки только отражает их в интерфейсе.

**Как защищено редактирование чужой заявки?** Выборка ограничена одновременно ID заявки,
гонкой и `driver__user=request.user`. Для чужого объекта возвращается 404.

**Зачем atomic и select_for_update?** Несколько запросов могут одновременно увидеть свободное
место. Транзакция и блокировка строки гонки сериализуют проверку вместимости и запись.
Уникальные ограничения дополнительно запрещают повторные номера и заявки.

**Почему автор комментария не является полем формы?** Иначе клиент мог бы подменить автора.
Сервер всегда устанавливает его из аутентифицированной сессии.

**Как хранятся пароли?** Django сохраняет хеш с солью, а не исходный пароль. Создание использует
`UserCreationForm`, демонстрационные пользователи — `set_password()`.

**Что защищает от XSS и CSRF?** Пользовательский текст экранируется шаблонизатором. POST-формы
передают CSRF-токен, который проверяет `CsrfViewMiddleware`.

**Зачем POST/Redirect/GET?** После успешной записи сервер перенаправляет на GET-страницу;
обновление страницы не повторяет отправку формы.

**Почему важна сортировка при пагинации?** Без детерминированного `order_by` записи могут
переходить между страницами. Используются дата / имя и первичный ключ как дополнительный критерий.

**Где именно Jinja2?** В `config/settings.py` настроен Jinja2 backend, в `config/jinja2.py` —
environment. Все клиентские страницы лежат в `templates/`; Django-admin использует свой backend.

**Можно ли разместить приложение на GitHub Pages?** Нет, Pages обслуживает статические файлы.
Там публикуется отчёт MkDocs; приложение требует Django-сервера и PostgreSQL.
